# Quality and acceptance evidence

Acceptance measures belong to an agreed church profile. A single-campus church and a network holding simultaneous services may choose different load and recovery targets. Both must define the targets, record test conditions and demonstrate the same financial, access and safeguarding invariants. Use fictitious people and book balances for all rehearsals.

| Concern | Repeatable exercise | Evidence and passing condition |
| --- | --- | --- |
| Concurrent editing | Two clerks edit different or conflicting fields from the same original member revision. | Neither loses an accepted edit. A conflict shows authorized differences and records the resolution. Historical changes retain the two actual actors. |
| Last unit of capacity | Two households request the last seat or the last copy of a book. One client retries after a timeout. | At most one allocation at capacity. Second request receives a known waiting/failed outcome. Repeating the winner's request does not duplicate stock or registration. |
| Access through derived views | Remove a role after someone saves a search, queues an export or opens a board pack. Change one independently authorized household contact's permissions. | Check list, detail, total, export, email preview, thumbnail, attachment, print queue, assistant and cached views. Independent personal access remains usable. Explanations do not reveal protected record existence. |
| Mobile and accessible operation | Complete member invitation, offering receipt, event registration and vote review with keyboard only, screen reader, 200% text size, touch and a constrained connection. | Labels, focus, error recovery, state announcements, formats and accessible printable equivalents can be used independently. No important action requires color, hover or a timed gesture alone. |
| Language and time | Use a right-to-left name, single-name member, multilingual notice, late-night event across two time zones, and a locally skipped or repeated clock time. | Preserve spelling and order, display the actual locale/zone, avoid ambiguous date parsing, apply the declared recurrence rule, and preserve the original approved text and time. |
| Load and responsiveness | Agree peak arrival rate, concurrent check-in stations, donation burst, report period, data volumes and maximum wait by action before rehearsal. Include background exports and slow providers. | Report throughput, failure count, queue age and 95th-percentile response time against the agreed budget. Hard limits for capacity, access and double entry hold even when a response exceeds its time budget. |
| External delivery and replay | Inject duplicate, delayed, reversed and out-of-order observations; force a timeout after external acceptance. | Correct final status and one business effect. An unknown outcome remains visible pending reconciliation. Staff can recover the failed receiver without paying, granting, mailing or posting again. |
| Offline safety | Build a scoped pack, revoke an authority centrally, disconnect the device, perform a permitted attendance action, reconnect, and present the old collection code. | Local changes are visibly pending; safe operations replay once. A stale code cannot complete a restricted release. Device loss triggers expiry and an authorized containment procedure. |
| Financial integrity | Recalculate the worked month and independent settlement after a partial return. Attempt to change a posted amount or approve one's own restricted payment. | Every posted journal balances, subledger/open items tie to controls, restricted-fund differences are identified, and a correcting entry preserves the original. |
| Retention, exit and recovery | Request a verified extract, place one record on hold, process a disposal and then restore a backup into isolation. | Include only authorized fields; preserve the held material; apply disposal and revocation history before reopening. Recovery evidence identifies any unrecoverable interval and its reconciliation owner. |
| Optional assistance | Using the same question, compare results for a public visitor, member, treasurer and departing staff user. Introduce a revoked or unsupported source. | Each answer stays within current authority, identifies its internal basis where factual, states uncertainty, and routes sensitive decisions to human owners. No data are sent to an unapproved destination. |

## Evidence to retain

For each acceptance run capture the church profile, enabled capabilities and policy versions; data snapshot and cutoff; inputs and actors; expected and observed records, statuses, amounts and totals; permitted and denied outputs; unresolved exceptions, owner and due date; and signed disposition. Record measured recovery point and recovery time at the point usable service was actually restored. Never attach production secrets, actual pastoral narratives or identifiable child records as proof of a test.

## Maintaining the specification

An added capability has one domain owner and an index entry written as a user task. Its dictionary identifies fields, meaning, types, keys, context, cardinalities and ownership. Its operating section captures permissions, lifecycle, evidence, reporting, ordinary and exceptional outcomes. If another module already owns the identity or transaction, link to it and say whether the new data is an extension, a projection or an independently approved fact. Add the record to the [catalogue](../reference/records.md), revisit affected handoffs, and add or amend a cross-domain fixture when an old answer could change.
